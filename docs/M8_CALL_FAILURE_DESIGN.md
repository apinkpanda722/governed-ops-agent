# M8 보정 호출 실패 대응 설계안 (문서만, 코드 변경 없음)

M8 추가 정리 — 공식 M6 수치 아님. 근거는 비용 원장 `data/manifest/costs_grading.jsonl`의 `m8:calibration:*` 행(비용 프로브 제외)이다. 원장에는 예약·정산 시각, 토큰, 비용만 있고 본문은 없다. 표본 ID와의 대응은 `make m8-grounding-diagnose`가 맞춘다(행 키 해시 → task → sample_id).

## 1. 관찰 (v3.0 첫 보정, 원장 37호출)

| 항목 | 값 |
|---|---|
| 호출 수 | 37 = 보정 30행 + 합성 주입 7 |
| 총 비용 | $0.7427 (단계 상한 $0.8) |
| **정산이 예약 추정과 정확히 같은 호출** | **5건, $0.3453 = 총액의 46.5%** |
| 그 5건의 예약~정산 간격 | 58.8~59.0초 (예약 시각과 정산 시각의 차) |
| 확인된 호출 32건의 간격 | 5.0~57.9초, 중앙값 17.7초(가장 긴 호출이 60초 한도 바로 아래) |
| 그 5건의 출력 토큰 | 모두 8192(= `MAX_OUTPUT_TOKENS`, 확인되지 않은 사용량을 예약 값으로 정산한 값) |
| 그 5건의 예약 입력 상한(`2*bytes+4096`) | 19,350 · 34,396 · 46,402 · 59,056 · 96,452 토큰 (표본 중 가장 큰 프롬프트들) |
| 확인된 호출 32건 | 비용 중앙값 약 $0.011, 최대 $0.034; 출력 토큰 최대 8,175 |
| 확인된 호출 중 출력 토큰 ≥ 8000 | 1건(8,175 토큰, $0.0342) |

## 2. 호출 실패 5건 (`grading_call_failure`)의 원인 후보

1. **60초 타임아웃 (가장 유력)**. 근거: 5건 모두 예약~정산 간격이 58.8~59.0초이고(확인된 호출은 5.0~57.9초, 중앙값 17.7초), 코드에 상한 두 곳이 있다: `grounding/grader.py`의 `asyncio.wait_for(..., timeout=60)`과 SDK `HttpOptions(timeout=60000)`. 5건은 입력이 가장 큰 프롬프트와 겹친다(큰 근거 + 사고 토큰 + 출력 상한 8192). 타임아웃은 일반 예외로 분류돼 `grading_call_failure`가 된다. 확인 수단: 사용자가 `diagnose-calibration`을 실행하면 실패 sample_id와 간격이 표로 나온다.
2. 429·5xx: 간격이 60초에 몰리지 않고 짧게 끝나야 하므로 이번 관찰과 맞지 않는다.
3. 응답 빈 값: 파싱 단계에서 걸러져 `grading_response_failure`로 분류되므로 이 5건이 아니다.
4. **상한 도달 시 남은 호출 거부는 call_failure로 세지 않는다.** `SpendCapError`는 `GradingError`의 하위 클래스가 아니고(`RuntimeError`), `grade()`는 예약 전에 이를 올리며 `_evaluate`가 `except GradingError`보다 뒤의 별도 분기에서 받아 `stop_code`로 기록하고 루프를 멈춘다. 따라서 call_failure 5건과 상한 중단은 독립이다. (이번 실행의 중단은 30행 채점이 끝난 뒤 합성 주입 도중에 일어났다: 호출 37 = 30 + 7.)

## 3. 응답 실패 1건 (`grading_response_failure`)의 원인 후보

1. **출력 한도 근접으로 JSON이 잘림 (가장 유력)**. 근거: 확인된 호출 중 출력 토큰이 8,175인 1건이 있다(8192 한도, 사고 토큰 합산). M6 r2의 `MAX_TOKENS` 실패와 같은 유형이다. 이 호출은 사용량이 확인돼 실제 비용($0.0342)으로 정산됐다.
2. 입력 연결 검증 실패: 채점기가 `cited_ids`·`citation_supports`의 ID 집합을 문장의 인용과 다르게 냄(`_validate_input_links`).
3. 응답 모델 이름이 `gemini-3.8-flash`로 시작하지 않음.
확인 수단: 위 1은 원장의 출력 토큰으로 이미 지지된다. 2·3은 이번 실행에서 사유가 저장되지 않았다. 앞으로의 실행은 `calibration-detail.jsonl`에 행별 상태와 코드가 남는다(이번 PR).

## 4. 설계안 (모두 새 등록 또는 사용자 결정 필요, 이 PR에서 구현하지 않음)

### 4-1. 타임아웃을 입력 크기에 비례해 늘린다
- 제안: 호출 타임아웃 = `clamp(60 s + 2 s × (예약 입력 상한 / 1000), 60 s, 240 s)`. SDK와 `wait_for` 두 값을 같이 바꾼다.
- 비용: 5건이 끝났다면 정산이 확정 사용량이 된다. 확인된 호출의 단가로 보면 큰 프롬프트는 호출당 약 $0.04~0.07(미실측)이고 이번 보수 정산($0.045~0.103)보다 적다. 단 "실패 5건의 데이터를 얻는다"는 점이 이득이고 총비용이 늘어날 수 있다(5행 채점 추가).
- 결정론: 온도 0·프롬프트·스키마·출력 한도는 그대로라 측정 의미가 바뀌지 않는다. 타임아웃은 현재 등록 문서에 없는 구현 파라미터이므로 변경 사실을 새 등록 파일에 적는다.

### 4-2. 단일 재시도는 도입하지 않는다 (권장)
- 같은 입력이 같은 이유(60초 초과)로 다시 실패할 가능성이 높아 비용만 두 번 쓴다(실패한 첫 시도는 보수 정산 그대로).
- 서버에서 첫 시도가 실제로 처리됐을 수 있어 이중 과금 위험이 있다(A-FP-035와 같은 원칙).
- 읽기 전용 호출이라 부작용 중복은 없지만, 재시도 결과를 채택하면 "같은 task를 한 번만 센다"는 재실행 규칙과 맞지 않는다.
- 재시도가 필요하면 429·5xx(응답을 받은 오류)에만 한정하고 시도 횟수·대기를 등록한다. 이번 관찰에는 해당 사례가 없다.

### 4-3. 실패한 호출의 보수 정산
- 현재: 확인되지 않은 사용량은 예약 추정으로 정산한다(ADR-007, 비용 상한 원칙). 이번에 총비용의 46.5%가 완료되지 않은 호출에 쓰였다.
- 선택지: (가) 유지, (나) 응답을 받지 못한 연결 단계 오류만 0으로 정산(구별 가능한 예외 종류가 있을 때만). 타임아웃은 서버가 처리했을 수 있어 (나)의 대상이 아니다.
- 권장: (가) 유지. 비용 상한 규칙(호출 직전 추정 검사, AGENTS.md CRITICAL)을 약화하지 않는다.

### 4-4. 예약 추정이 상한 도달을 앞당기는 문제
- 예약 추정($0.04~0.10)은 확인된 비용(중앙값 약 $0.011)의 약 4~6배이고, 호출 직전에 남은 상한이 다음 호출의 추정보다 작으면 중단된다. 이번에도 실제 소진은 $0.7427이었지만 남은 약 $0.057이 마지막 호출의 추정보다 작아져 멈췄다.
- 선택지: M8 단계 상한의 검사에만 추정 대신 관측 분포(예: 확인된 호출의 95번째 백분위 × 여유)를 쓰는 안은 새 등록이 필요하고, 공급사 상한 검사(`CostLedger.reserve`)는 그대로 둔다. 구현 전에 사용자 결정이 필요하다.

### 4-5. 응답 실패(출력 한도 근접) 완화
- `max_output_tokens` 8192는 등록 값이라 올리지 않는다(올리려면 새 등록).
- 프롬프트 개정(v3.1 이상)으로 출력을 줄일 수는 있다(허용: 문구·루브릭 설명, 금지: 출력 스키마 의미 변경). 예: `evidence_ids`를 판정에 쓴 항목만 내도록 지시.
- 사고 토큰 예산 제한은 SDK 설정이므로 새 등록이 필요하다(모델·온도·스키마 의미와는 별개 항목).
