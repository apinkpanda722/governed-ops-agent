## 기록 파일과 키 순서 결함

- 기록: `data/replay/llm/<task>.jsonl`(LLM 응답), `data/replay/a_run/<task>.jsonl`(그 실행에서 실제로 나간 A 호출의 응답), `data/replay/golden/status.json`. 기록 파일에 비밀값과 비합성 문서는 없다(검사 테스트 통과).
- **결함**: 도구 결과는 LLM 메시지에 JSON 문자열로 들어간다. live는 A 응답의 필드 순서(`doc_id, title, is_current, date, text`)이고, 기록 파일은 A 응답을 키 정렬로 저장해 재생 메시지의 키 순서가 달라져 요청 키가 맞지 않았다. 도구 결과가 있는 호출(2번째 호출부터)에서 "재기록 필요"로 실패했다. 이전 합성 기록 테스트에서는 가짜 A의 키 순서가 우연히 정렬 순서와 같아 드러나지 않았다.
- **발견 경위**: 기록을 커밋하기 전 골든 재생 검사에서 7개 중 T1-01 등이 실패해 발견했다. 프롬프트 해시는 일치했다.
- **처리**: 요청 키 계산이 도구 결과 JSON을 키 순서와 무관하게 비교하도록 고쳤고(`replay/llm.py`), 기존 기록은 **기존 방식 키가 기록된 `request_key`와 정확히 일치함을 확인한 뒤** `request_key`만 새 방식으로 바꿨다(`scripts/rekey_llm_records.py`, 로직은 `evalrun/rekey.py`). live 키 순서는 계약 스냅샷 출력 스키마의 `required` 배열(응답 모델 필드 순서)에서 가져왔고 손으로 적은 순서는 없다(mock-jira 응답은 인프로세스 mock이 돌려주는 순서). 응답·사용량·비용 등 다른 필드는 바꾸지 않았다. dev 결과(7/7)는 그대로 공식 결과다. 하나라도 불일치했다면 아무 파일도 바꾸지 않고 dev 전체를 다시 실행하기로(이전 실행 보존, 사유 "기록 재생 키 결함으로 골든 재생 불가, 결과와 무관") 정해 두었으나 불일치는 없었다.
