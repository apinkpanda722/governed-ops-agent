## ADR-014 비교 지표 (T5 단계 수·p95 지연)

정의: **단계 수** = task trace의 `kind=model_call` span 수. **지연** = task trace의 루트 span `duration_ms` 합(승인 대기 시간은 span 밖이라 포함되지 않는다). p95는 nearest-rank다. n이 작아 유의성은 주장하지 않는다.

## T6-01 — 이번 두 실행에서 실패

T6-01(거부 시나리오)은 두 실행 모두 `search_docs` → `get_document` 뒤 세 번째 모델 응답이 도구 호출 없는 요약 텍스트였다. 초안(`slack_send_message`)이 제출되지 않아 승인·거부 단계가 없고 `reject_not_recorded`다. 세 번째 실행 이전 기록(첫·두 번째·세 번째 실행)은 세 번째 응답이 `slack_send_message`(또는 거부까지 진행)였고 통과했다.

- 첫 모델 요청의 `request_key`는 세 번째 실행·끔·켬 세 기록 모두 `603e6ed8…`로 같다(단일 턴 요청 경로 불변). 두 번째 요청부터 키가 세 기록 모두 다르다. 세 번째 응답이 세 번째 실행에서는 `slack_send_message` 호출이고 끔·켬에서는 텍스트다.
- trace 루트 span의 `final_status`는 두 실행 모두 `completed`(그래프가 도구 호출 없는 답으로 끝남)이고 관측 `status`는 `failed`다. 차이는 러너가 만든다: `build_observation_m3`는 승인 스크립트(거부 단계)가 남아 있으면(`plan_remaining > 0`) 상태를 `failed`로 기록한다. 그래프 상태가 아니라 러너의 판정 규칙이다.

## 경과: 스모크가 잡은 서비스 결함 3건

1. **`make serve` 시작 교착(1회차)**: `startup_cleanup`이 checkpointer 목록 조회(`alist`, 잠금을 쥔 채 yield) 안에서 같은 checkpointer를 다시 호출해 `asyncio.Lock`을 기다렸다. M3 코드부터 있던 결함이며 DB에 thread가 있을 때 재현됐다. 수정 PR #91(FP-068), 재live에서 `make serve`가 기동했다.

3. **새 대화 라우트가 자리표시자 서비스를 사용(재live)**: 실제 서버 진입점은 `TaskService(None)` 자리표시자로 앱을 만들고 lifespan에서 `app.state.task_service`를 교체하는데, `POST /conversations`·`POST /conversations/{id}/turns`·`GET /conversations/{id}`·`GET /approvals`가 생성 시점의 클로저 서비스를 써서 500이었다(`FAIL rag_turn1 request_failed:HTTPStatusError`). 같은 유형으로 `app.state.audit`가 자리표시자의 `None`으로 남아 실제 서버에서 `auth.failed` 감사가 기록되지 않았다. 모든 라우트가 `request.app.state.task_service` 한 곳에서 서비스를 얻도록 고치고 lifespan이 `app.state.audit`도 갱신한다. 회귀 테스트는 실제 진입점(`build_server_config`)을 거친다. 수정 PR #93(FP-070), 재live에서 `rag_turn1`부터 PASS했다.

## 한계

- 만료됐지만 조회되지 않은 승인 대기가 prune으로 지워지면 `approval.expired` 감사 기록이 없다(만료 처리는 조회·새 턴 요청 때만 일어난다).
- 지난 턴의 늦은 중복 승인은 404다(영수증은 현재 턴에만 있다).
- 이 결과의 dev는 단일 턴이다. 멀티턴 경로는 dev 실행으로 검증되지 않았고 위 재live 스모크 1회로만 확인했다(평가 범위 밖). 스모크는 두 번의 시도에서 서비스 결함 3건을 잡았다(위 경과).
- live로 확인하지 않은 항목: ① serve 재시작 뒤 세션 소멸과 로그인 화면 이동, ② 승인 대기 중 재시작 뒤 승인 재개는 단위 테스트로만 확인했다. ③ 후속 질문 턴(읽기 턴)의 맥락 이월은 스모크에서 쓰기 턴(`share`)으로만 확인했고, 읽기 후속 질문이 이전 답변을 참조하는 동작은 live로 확인하지 않았다.
- dev는 task당 1회라 실행 간 도구 선택 변동(T3-01)과 응답 변동(T6-01)이 TCR에 그대로 반영된다. test는 task당 3회라 pass^3으로 드러난다.
- 켬과 끔 사이의 T5 단계 수·지연 차이는 탐색 예산이 개입하지 않은 두 실행 사이의 변동이어서 탐색 예산의 효과를 보여 주지 않는다.
- 평가 경로는 in-process ASGI로 실제 API 코드를 거치지만 실제 서버 프로세스와 세션 TTL은 거치지 않는다.
- 훅 소요는 사전 판정 시간이며 모델 응답 지연이 아니다.
