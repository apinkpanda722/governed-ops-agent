# M2 관측 live 실측 (m2-obs)

사용자가 `m2-obs` 머지 후 live 환경에서 실행한 Langfuse 첫 기동과 `make smoke-obs`의 결과, 원인 분석, 수정 내용이다. 키·토큰·본문 값은 이 문서에 없다.

## 실행 조건

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-04 |
| 코드 커밋 | main `cbdda82`(PR #18 머지) |
| 모드 | live (compose 핵심 스택 + profile `obs`, LiteLLM 경유 OpenAI) |
| Langfuse 서버 / SDK | `langfuse/langfuse` 3.225.11 / Python `langfuse` 4.16.0 |
| LiteLLM | `v1.103.3`, 설정 `infra/litellm/config.obs.yaml`(`turn_off_message_logging: true`) |
| 모델 | LiteLLM 별칭 `agent-primary` → `gpt-6-luna` (fallback·Guardrail 없음) |
| 비용 | 원장 `data/manifest/costs.jsonl`에 `agent_primary` 행으로 기록(`make cost-report`로 확인) |

## smoke-obs 1차 실행: 전부 실패

기대값은 실행 전에 코드에 고정되어 있었다(`E1`~`E7`).

| 기대값 | 결과 |
|---|---|
| E1 trace 존재 | FAIL |
| E2 에이전트 span | FAIL |
| E3 LiteLLM generation 연결 | FAIL |
| E4 generation 내용 비어 있음 | FAIL |
| E5 PII 마스킹 | FAIL |
| E6 비밀 값 부재 | FAIL |
| E7 JSONL·Langfuse span 수 일치 | FAIL |
| INFO `annotation_queues_status` | 200 |

조사 결과(읽기 전용 확인):

- ClickHouse의 `traces`·`observations`가 0건이다. 데이터가 Langfuse에 전혀 도착하지 않았다.
- **원인 A — LiteLLM generation 업로드 실패**: `langfuse-web` 로그에서 LiteLLM 콜백의 generation 업로드가 9건 실패했다. 객체 이름이 `events/<project>/observation/time-<시각>_resp_<긴 base64>…`이고 MinIO가 `XMinioInvalidObjectName: Object name contains unsupported characters`로 거부했다. 이어서 `Failed to upload events to blob storage, aborting event processing`이 기록됐다. LiteLLM이 응답 ID로 만든 긴 기본 generation ID가 객체 이름 제한에 걸린 것이다.
- **원인 B — 에이전트 span이 도착하지 않음(업로드 실패 로그도 없음)**: SDK 4.16.0(v4)과 서버 3.225.11은 호환된다(공식 호환 표: Python SDK v3·v4는 서버 3.63.0 이상). 원인은 우리 sink가 만든 tracer의 계측 범위(scope)에 `public_key` 속성이 없는 것이었다. Langfuse span 프로세서는 범위 이름이 `langfuse-sdk`인 span에 대해 같은 프로젝트의 `public_key` 범위 속성을 요구하고, 없으면 debug 로그만 남기고 span을 **조용히 버린다**. 루프백 OTLP 수신기로 재현했다: 수정 전에는 `flush` 후에도 전송 0건, 수정 후에는 `/api/public/otel/v1/traces`로 전송된다.
- worker의 `monitors`·`batch_actions`·`background_migrations` 테이블 없음 오류는 기동 직후 마이그레이션 경합이었고 확인 시점에는 테이블이 모두 있었다(무시).
- annotation queue API는 HTTP 200이다. 셀프호스팅 3.225.11에 포함된 것으로 확정했다.

## 수정 (`fix/m2-obs-langfuse`)

1. **tracer 범위 속성**: `get_tracer("langfuse-sdk", attributes={"public_key": ...})`. 실제 SDK·OTel 내보내기를 루프백 서버로 확인하는 회귀 테스트를 추가했다(수정 전 실패, 수정 후 통과). trace ID·부모 span 관계·마스킹된 페이로드·flush 시점·종료 시 shutdown 등록을 검증한다.
2. **LiteLLM generation ID**: 요청 메타데이터 `generation_id`에 16자리 hex(`secrets.token_hex(8)`)를 넘기고(LiteLLM 공식 문서의 generation 파라미터), 같은 값을 모델 호출 span 속성 `generation_id`에 기록한다.
3. **`smoke-obs` E3 강화**: LiteLLM generation의 ID가 에이전트의 모델 호출 span이 기록한 `generation_id` 중 하나여야 한다(지정한 ID가 실제로 쓰였는지 확인).
4. **문서**: ADR-009 본문·ARCHITECTURE·EVAL에서 annotation queue 포함 여부를 확정(API 200, 2026-10-04)하고 generation ID 결정을 반영했다.

## smoke-obs 2차 실행(1차 수정 후): 전부 FAIL이지만 데이터는 도착

1차 수정 후 `make obs-up` → `make smoke-obs`를 다시 실행했다. 결과는 `E1`~`E7` 전부 FAIL(INFO `annotation_queues_status=200`)이었다. 읽기 전용 확인(trace `2aff0ecd…`)은 다음과 같다.

- Langfuse API `GET /api/public/traces/<id>`가 200, id 일치, observations 14개: GENERATION `agent-primary` 3, SPAN `task` 1·`model` 3·`agent-primary` 3·`read_tools` 2, TOOL `lookup_id`·`get_document`. trace input에 PII 자리 표시(`[PII:…]`)가 있다.
- 로컬 `logs/traces/<id>.jsonl` 11행(graph_node 5, model_call 3, tool_call 2, task 1). model_call의 `generation_id` 3개가 있고 Langfuse generation ID도 16자리 hex다. 즉 1차 수정(tracer 범위 속성, generation ID)은 효과가 있었다.
- 데이터가 도착했는데 전부 FAIL이었으므로 smoke 판정에 결함이 있었다. 코드를 읽어 확인한 원인:
  1. **마감 직전 조회가 판정을 지움**: 조회 루프가 마감 시각까지 돌고, 마지막 조회는 남은 시간(약 0.01초)을 시간 제한으로 써서 거의 항상 시간 초과가 났다. 이 실패가 앞선 조회의 판정을 모두 `False`로 덮어썼다. `E4`가 실제로 불합격이면 루프는 마감까지 돌므로 항상 이 경로로 전부 FAIL이 됐다.
  2. **예외를 삼킴**: 바깥 `except`가 어느 단계에서 어떤 예외인지 알리지 않고 전부 `False`로 덮었다.
- **실제 결함 후보 — E4**: GENERATION 3개 모두 input이 비어 있지 않았다. LiteLLM 공식 소스(`redact_messages.py`, main 기준)는 원문 로깅을 끄면 messages를 `[{"role":"user","content":"redacted-by-litellm"}]`로, 응답 내용과 도구 호출 인자를 `redacted-by-litellm`으로 **바꿔 보낸다(비우지 않는다)**. 따라서 input이 비어 있지 않은 것이 곧 원문이 나갔다는 뜻은 아닐 수 있다. `v1.103.3`에서의 실제 내용은 아래 재실행에서 사유 코드로 확인한다(가설이며 확정이 아니다).
- `make obs-up` 출력에서 litellm이 재생성되지 않고 `Running`으로 남았다. 1차 실행 때 이미 obs 설정으로 재생성되어 있었으므로 이 자체는 정상이다. 다만 바인드 마운트한 `config.obs.yaml`의 **내용만** 바뀌면 compose가 재생성하지 않아 오래된 설정이 남는 위험이 있다.
- GENERATION이 모델 호출 span 아래가 아니라 trace 최상위에 붙었다(`parentObservationId` 없음).

## 수정 (`fix/m2-obs-langfuse`, 2차)

1. **smoke 진단성·판정 보존**: 마지막으로 성공한 조회의 판정을 보존하고(이후의 실패한 조회가 지우지 않는다), 마감 직전 조회도 최소 5초를 기다린다. 실패 시 단계(`task_run`/`trace_fetch`/`checks`)와 예외 **클래스 이름만** `INFO stage=… exception=…`으로 출력한다. 검사별 FAIL 줄에 짧은 사유 코드를 붙인다(예: `FAIL E4_NO_MESSAGE_CONTENT: generation_not_redacted=3`, `FAIL E1_TRACE_EXISTS: trace_fetch_status=401`). 메시지·URL·키·본문은 출력하지 않는다.
2. **E4 재정의**: 비었거나 `redacted-by-litellm` 자리 표시자가 있고 요청 문구(전화번호 프로브, 장애 번호)가 generation에 없으면 통과다. 사유 코드: `generation_not_redacted=n`(내용이 있는데 자리 표시자도 없음), `request_text_in_generation=n`(요청 문구가 나감).
3. **`make obs-up`**: LiteLLM을 항상 `--force-recreate`한다. `config.obs.yaml`의 `litellm_settings.turn_off_message_logging: true`는 공식 문서(proxy/logging)의 위치와 같고 테스트로 고정했다.
4. **generation을 모델 호출 span 아래로**: 요청 메타데이터 `parent_observation_id`에 현재 모델 호출 span ID를 넘긴다(LiteLLM 공식 문서의 generation 파라미터). 동작은 `smoke-obs`의 `INFO generations_under_model_span=<붙은 수>/<전체>`로 확인하며 합격 조건은 아니다. 붙지 않으면 한계로 기록한다.
