## 알려진 한계

- **개방형 요청의 단계 상한 도달**: 브라우저 데모에서 "INC-2026-012 장애보고에서 원인과 조치 내용을 목록으로 정리해줘"가 `failed`로 끝났다. trace(`e5d25ab4d383401db474f9ff82c29774`)의 `task` span은 `final_status: failed`, `error_code: max_steps`, `steps: 8`이며 모델 호출 8회(`gpt-6-luna`, 모두 ok, fallback 없음)의 비용 합은 $0.00204다. 도구 순서는 `lookup_id` → `search_docs` → `run_sql` → `jira_get_ticket` → `search_docs` ×4이고, 4번의 문서 검색이 매번 새 문서 ID(6·2·4·2개)를 돌려줘 탐색 카운터의 최대 연속 무정보 횟수는 1이었다. 그래서 탐색 예산(N=4)이 아니라 단계 상한(8)에서 닫혔고, 사용자 화면에는 모든 `failed`에 같은 고정 문구가 나온다. 예산 소진은 `read_tools` 노드 끝에서 먼저 판정되므로 처리 순서의 결함은 아니다.
  - dev 20개에는 개방형 요청(여러 문서를 훑어 정리하는 요청)이 없고 dev 전체의 최대 단계 수는 5다(dev3·dev4 켬·끔·dev5 모두 `max_steps` 실패 0건). 이번 증상은 dev로 관측되지 않는다.
  - 같은 질문의 브라우저 시도는 5번 중 2번이 `max_steps`로 실패했다. platform 사용자는 4번 중 1번(위 trace)이고, 같은 요청을 새 대화 3개로 다시 보낸 3번은 모두 성공했으며 도구 2단계(ID 조회, 문서 읽기)였다. finance 사용자는 1번 중 1번 실패했고, 문서 읽기 권한 실패 뒤 같은 검색을 반복하다 단계 상한에 걸렸다. 같은 프로필(`writes_team`)에서 성공과 실패가 섞여 모델 변동으로 정리하며 `writes_org`와의 비교는 하지 않았다.
  - 화면 문구는 모든 `failed`에 같다(`error` 코드별 분기는 다음 수정 phase에서 한다). 원인은 코드별로 구분되지만 사용자는 구분하지 못한다.
  - 단계 상한 도달 시 근거를 모아 마지막 답변을 한 번 더 만드는 방안(a안)은 적용하지 않았다. M6 첫 phase 후보다.
- **실패 사유는 서버 로그에 남지 않는다**: `make serve`는 `uvicorn.Config(..., access_log=False)`이고 `api/` 계층에 로거가 없다. 실패 사유(`error_code`)는 trace에만 남는다. 코드는 바꾸지 않았다.
- **수신처 차단 경로의 골든 커버리지**: 실제 모델 응답을 기록해 전체 그래프를 재생하며 `recipient_not_allowed`를 지나는 골든 케이스는 T5-11뿐이었고, 이번 실행의 T5-11은 모델의 자기 거절로 그 경로를 지나지 않는다. 새 골든 케이스는 추가하지 않았다. 이 경로는 결정론 검사 단위 테스트(`tests/test_checks_draft.py`, `tests/test_agent_scope.py`), API 뷰 테스트(`tests/test_api_ui_contract.py`, `tests/test_api_blocked_view.py`)와 e2e 백엔드의 `다른 팀 채널` 시나리오(`tests/test_e2e_backend.py`)가 덮는다.
- dev는 task당 1회라 실행 간 도구 선택 변동(T3-01, T6-01)이 TCR에 그대로 반영된다. test는 task당 3회라 pass^3으로 드러난다.
- dev는 단일 턴이다. 멀티턴 경로는 dev 실행으로 검증되지 않았다.
- 훅 소요는 사전 판정 시간이며 모델 응답 지연이 아니다.
