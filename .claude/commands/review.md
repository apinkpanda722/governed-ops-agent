이 프로젝트의 변경 사항을 리뷰하라.

먼저 다음 문서들을 읽어라:
- `/AGENTS.md`
- `/docs/` 하위 문서 전부 (ARCHITECTURE, ADR, 그리고 프로젝트가 추가한 기준 문서)
- `/.claude/skills/failure-patterns/SKILL.md`

그런 다음 변경된 파일들을 확인하고, 아래 체크리스트로 검증하라:

## 체크리스트

1. **아키텍처 준수**: ARCHITECTURE.md에 정의된 디렉토리 구조를 따르고 있는가?
2. **기술 스택 준수**: ADR에 정의된 기술 선택을 벗어나지 않았는가?
3. **테스트 존재**: 새로운 기능에 대한 테스트가 작성되어 있는가?
4. **CRITICAL 규칙**: AGENTS.md의 CRITICAL 규칙을 위반하지 않았는가?
5. **검증 통과**: `make verify`가 에러 없이 통과하는가?
6. **프로젝트 기준 문서**: 프로젝트가 `/docs/`에 추가한 기준(UI 가이드, 평가 기준 등)이 있다면 그 기준을 지키는가? 수치 기준이 있다면 이전 결과보다 나빠지지 않았는가?
7. **실패 패턴**: 변경된 코드·테스트에 failure-patterns의 패턴(FP-NNN)이 다시 나타나지 않는가? 특히 확정 실패(`FAILED`)와 불확실(`UNCERTAIN`)의 구분(FP-001), 식별자·해시에 PII 정규식을 돌리는지(FP-010), 무작위·난수·`uuid`를 `monkeypatch`로 고정해 간헐적 실패를 가렸는지(FP-011), 동시 실행 결과의 순서를 단언하는지(FP-012), 외부 서비스 응답을 가짜 응답으로만 검증하는지(FP-020), 합격 조건이 한 지표만 보는지(FP-021), 기본값이 있는 환경 변수를 `env_or`로 읽는지(FP-030), 주입한 장애가 시험하려는 검사 경로를 실제로 타는지(FP-005), 0건 지표를 짝 지표(누락·최종 상태) 없이 판정하는지(FP-040), 상태를 다른 판정 범주로 매핑하면서 원래 의미를 증명하는 기록을 요구하는지(FP-041), 실행 경로가 정답지·평가 데이터를 읽는지(FP-042), 기대값이 실행 전에 같은 커밋으로 등록됐는지(FP-043). 같은 판정에 진입점이나 규칙 버전이 둘인지(FP-044), 세는 대상 정의가 다른 두 기록을 비교하는지(FP-045), 중간 step에서 완화한 테스트(`require_all=False`·슬라이스 비교)가 복원됐는지(FP-056), git 이력·I/O 지연·가상 시간에 의존해 CI에서만 실패할 테스트가 없는지(FP-032). 또한 **데이터에 기반한 판단의 근거가 원자료인가**(도구 출력은 `data/replay/a_run/`·`data/contract/`·live 출력, 가공한 관측 파일 금지, FP-022).
8. **요청 반영**: 이번 phase 중 요청된 수정 항목이 모두 커밋에 반영됐는가? (A-FP-041)
9. **step 범위 밖 변경**: `git diff --stat`의 변경 파일이 각 step이 허용한 범위 안인가? 특히 `.claude/`와 `docs/results/`의 사전 등록 파일이 지시 없이 바뀌지 않았는가(FP-055).
10. **외부 계약 실측 목록**: 설계 초안의 "외부 계약 실측 목록"과 "첫 live에서 터질 수 있는 것" 목록이 있고 구현(preflight·smoke·픽스처)이 그 목록과 대응하는가(FP-050·FP-051).
11. **머지 후 사용자 실행**: PR 본문에 "머지 후 사용자 실행" 절이 있고 mock 이미지 재빌드, LiteLLM 재시작, 가상 키 갱신, 사용자 실행 산출물(원장) 커밋 필요 여부가 점검되어 있는가(FP-052, FP-031).

## 실패 패턴 등록

이번 phase에서 새로 겪은 실패(수정 커밋이 있었던 것)를 failure-patterns에 FP 항목으로 추가하는 초안을 제시하라. 기계적으로 검사할 수 있는 것은 강제 수단에 테스트 이름을 적고, 아직 테스트가 없으면 테스트 추가를 제안하라.
